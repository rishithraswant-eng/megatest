================================================================================
IMPLEMENTATION PLAN - 5 PHASES - REV. 2
AI Incident Report Assistant
RESTRUCTURED PER REQUEST: kit-dependent work is clubbed into Phases 1-2 so
it finishes as early and as contained as possible. Phases 3-4 are designed
to need ZERO kit access, so they can be built in parallel, in two separate
locations, by two different people/sub-teams, against a fixed interface
contract instead of the real hardware. Phase 5 is the merge: real models
swapped in for stubs, plus the UI/app shell finished end to end.
Rule retained from REV. 1: each phase owns exactly one major portion. No
phase mixes in work that belongs to another phase.
================================================================================

--------------------------------------------------------------------------------
THE CONTRACT THAT MAKES THE SPLIT POSSIBLE
--------------------------------------------------------------------------------
Phases 3 and 4 do not touch the kit because they are built against a fixed
"Conversation Engine" interface, not against the real models directly.
Phase 1-2 owns producing that interface for real, on-device. Phases 3-4 own
building a STUB implementation of the exact same interface (canned
responses, fixtures, scripted test conversations) and writing all app
logic against it. Phase 5's job is almost entirely swapping the stub for
the real thing and fixing whatever breaks at the seam.

Interface (minimum shape, owned/finalized by end of Phase 1):
  process_turn(session_id, audio_or_text_input) -> {
      transcript: {text, is_final, lang_detected},
      dialogue_act: "answer"|"correction"|"negation"|"uncertainty"|
                    "confirmation"|null,
      candidate_incident_types: [{incident_type_id, confidence}],
      candidate_fields: [{field_name, value, confidence, provenance}],
      function_calls_made: [{function_name, arguments, result}],
      assistant_followup_text: string | null,
      assistant_followup_audio_ref: string | null
  }
Everything in 03_TRD.txt section 5 (the function-calling allowlist) is
implemented behind this interface, not re-implemented by Phases 3-4.

--------------------------------------------------------------------------------
PHASE 1 - KIT BRING-UP AND MODEL SELECTION
          (kit required; aim to clear this fast -- it unblocks everything)
--------------------------------------------------------------------------------
Scope (and only this):
  - Confirm the exact QIDK chipset variant, RAM, and OS build (the open
    item in 03_TRD.txt section 1) -- do this literally first, before any
    model benchmarking, since it gates every size decision below.
  - Decide, in writing, which component owns Hindi/code-mixed handling
    (ASR vs. semantic model vs. an added normalization step) -- this is
    FR3 in 06_PRD.txt and must not be left implicit.
  - Stand up the QAIRT/QNN toolchain and get ONE trivial model running
    on-device end to end, to de-risk the pipeline before investing in
    real candidates.
  - Benchmark the ASR candidates (Whisper-Base/Small vs. Qwen3-ASR-0.6B)
    for streaming behavior, Hindi/code-mixed accuracy, and latency, on
    the actual kit.
  - Benchmark the LNN candidates (custom CfC vs. LFM2.5-230M/1.2B-Instruct)
    for the three required tasks (classification, dialogue-act, candidate
    extraction), including whichever one was assigned Hindi handling above.
  - Benchmark the semantic-model candidates (Qwen3-1.7B no-think,
    Qwen3-0.6B, Qwen3.5-0.8B) for per-turn latency and extraction/
    function-calling quality.
  - Benchmark the TTS candidates (MeloTTS-EN, Kokoro-82M) for synthesis
    latency and interrupt-ability.
  - Get basic mic capture + echo-cancelled audio I/O working on the kit's
    actual hardware (peripherals, not a laptop mic).

Explicitly NOT in this phase:
  - No conversation-state logic, no form/department routing, no REVIEW
    behavior, no UI screens, no database schema beyond whatever minimal
    fixture is needed to run a benchmark.

Exit criteria:
  - A written decision for: exact hardware target, Hindi-handling owner,
    and the selected ASR/LNN/semantic-model/TTS combination, each backed
    by a number (accuracy, latency, memory, power/thermal) measured on
    the physical kit -- not a spec-sheet guess.

--------------------------------------------------------------------------------
PHASE 2 - ON-DEVICE PIPELINE INTEGRATION
          (kit required; the only other kit-bound phase -- Phases 1 and 2
          together are the full kit-dependent portion of this project)
--------------------------------------------------------------------------------
Scope (and only this):
  - Wire the Phase 1-selected ASR + LNN + semantic model + TTS together
    into one running, on-device turn-processing loop implementing the
    Conversation Engine interface defined above, for real.
  - Implement the function-calling execution path on-device (the model
    actually deciding to call get_zone_details/get_form_fields/etc. from
    03_TRD.txt section 5) against a minimal local DB fixture -- not yet
    the full schema from Phase 3/4, just enough to prove real calls work.
  - Implement barge-in/interruption and echo cancellation at the real
    audio-pipeline level (not simulated).
  - Measure end-to-end per-turn latency against the P95 targets in
    03_TRD.txt section 6, on-device, and tune until within budget or
    document the gap.
  - Measure power/thermal behavior under a sustained conversation (several
    turns back to back), since this is where a dev kit can throttle.
  - Freeze and document the Conversation Engine interface's exact
    input/output shape -- this is the deliverable Phases 3-4 build against.

Explicitly NOT in this phase:
  - No department/incident-type routing logic, no form engine, no
    REVIEW/correction logic, no map/queue UI -- those are app-layer and
    belong to Phase 3/4/5 even though it would be tempting to sketch them
    here while the models are already warm.

Exit criteria:
  - A live, on-device demo of raw turn-processing (speak -> transcript ->
    classification/extraction -> at least one real function call ->
    spoken follow-up), meeting or documented against the latency targets,
    with the interface frozen and written down for Phases 3-4 to consume.
  - KIT IS NOT NEEDED AGAIN until Phase 5. From here, whoever has the kit
    is free to keep tuning/benchmarking in the background, but the
    project's forward progress no longer depends on it.

--------------------------------------------------------------------------------
PHASE 3 - ROUTING AND FORM ENGINE  (NO KIT NEEDED -- PARALLEL WORK-STREAM A)
--------------------------------------------------------------------------------
Can start the moment Phase 2's interface is frozen (does not need to wait
for Phase 2's on-device tuning to be "done," just for the interface shape
to be fixed) -- and can run at a second location with no kit present.

Scope (and only this):
  - Full database schema from 02_DATABASE_SCHEMA.txt: organizations,
    zones, departments, incident_types, form_fields, users,
    admin_credentials, draft_sessions.
  - Admin Mode screens for Environment Setup, Zone Editor, and the
    Department & Incident-Type Editor (05_UIUX_REQUIREMENTS.txt 1.1-1.4),
    including the form-builder behavior (add/edit/reorder required and
    clarifying fields per incident type).
  - The IDENTIFY stage logic: taking a Conversation Engine output
    (candidate_incident_types), deciding confident-match vs.
    disambiguation vs. multi-incident-narration, per 04_DESIGN_FLOW.txt
    steps 3 and the DISAMBIGUATING state.
  - The FORM_FILLING stage logic: reading form_fields, tracking
    extracted_fields status (missing/known/unknown/ambiguous), accepting
    "I don't know," never re-asking a known/unknown field.
  - The CLARIFYING stage logic: the stopping rule (diminishing returns /
    user "enough" / max-question bound).
  - All of the above built and tested against a STUB Conversation Engine
    (canned/scripted responses matching the frozen interface) -- never
    against real models.

Explicitly NOT in this phase:
  - No REVIEW/correction logic, no versioning/rollback, no admin auth
    enforcement beyond the schema existing, no map/queue rendering, no
    GNN/DynoTears -- those are Phase 4 or Phase 5.

Exit criteria:
  - Given a scripted sequence of stub Conversation Engine outputs
    (including an ambiguous case and a multi-incident case), the
    routing/form engine correctly identifies type/department, fills the
    right fields, asks only for genuinely missing ones, and correctly
    stops clarifying -- fully demonstrable with zero kit involvement.

--------------------------------------------------------------------------------
PHASE 4 - REVIEW, TRUST, AND RELIABILITY LAYER  (NO KIT NEEDED -- PARALLEL
          WORK-STREAM B, run alongside Phase 3 at a second location)
--------------------------------------------------------------------------------
Can start on the same trigger as Phase 3 (interface frozen) and should be
staffed/located separately from Phase 3 so both proceed genuinely in
parallel.

Scope (and only this):
  - The REVIEW stage logic: composing a summary from current
    extracted_fields, and the four actions (Confirm / Correct a detail /
    Skip remaining clarification / Cancel) from 04_DESIGN_FLOW.txt step 7.
  - Correction handling: field re-opening, draft_revision increment,
    correction_history rows, and invalidation of derived predictions
    (e.g. a stale priority classification) tied to a corrected field.
  - SUBMIT transaction logic: incidents row creation from a confirmed
    draft_session, duplicate-submission protection, and the
    local_submission_only flag discipline (never claim delivery without a
    real mechanism).
  - admin_credentials auth/role enforcement (not just schema -- actual
    login + permission checks).
  - schema_versions/model_versions versioning and rollback plumbing.
  - The validation/testing harness from 03_TRD.txt section 8: running
    held-out scripted conversations through the stub engine and
    computing field accuracy, routing accuracy, false-fill rate,
    repeated-question rate, completion rate.
  - (Optional, time-permitting, lowest priority in this phase) a first
    prototype of the GNN incident-relatedness computation against seeded
    fixture data, and/or the DynoTears-style batch job -- both still
    schema-ready and explicitly optional per 03_TRD.txt section 10.
  - All of the above built and tested against the same STUB Conversation
    Engine interface used by Phase 3, plus Phase 3's own output (so this
    phase needs Phase 3's draft_sessions/extracted_fields shape to be
    real, but not Phase 3's UI).

Explicitly NOT in this phase:
  - No IDENTIFY/FORM_FILLING/CLARIFYING logic (that's Phase 3's), no UI
    polish, no map/queue rendering -- Phase 5.

Exit criteria:
  - Given a stub-driven draft session reaching REVIEW, all four review
    actions behave correctly (including a correction that properly
    invalidates a derived field and forces re-confirmation), SUBMIT is
    idempotent and transactional, admin login/roles are enforced, and the
    validation harness produces real numbers against at least one
    scripted held-out conversation set -- all with zero kit involvement.

--------------------------------------------------------------------------------
PHASE 5 - MERGE, UI, AND APP FORMATION
          (kit required again, for final integration and rehearsal only)
--------------------------------------------------------------------------------
Scope (and only this):
  - Swap Phase 3/4's stub Conversation Engine for Phase 2's real,
    on-device one. Fix whatever breaks at the seam (timing assumptions,
    shape mismatches the stub didn't exercise, real latency changing UX
    timing).
  - Build/finish the actual UI screens end to end: all of Admin Mode
    (1.1-1.8) and User Mode (2.1-2.8) from 05_UIUX_REQUIREMENTS.txt,
    including the streaming tentative/final caption rendering, the
    4-state field indicators, barge-in visual feedback, department
    queues, the live map, and draft recovery prompts.
  - Full end-to-end integration pass: every journey in 07_APP_FLOW.txt,
    especially Journey D (the judge walkthrough), run for real on the kit.
  - Rehearse with the network disabled, timing the full flow, and fixing
    any rough edges found only once Phase 1-4's pieces are actually
    talking to each other and to a human.

Explicitly NOT new work in this phase:
  - No new NLU/model work (Phase 1-2's job), no new routing/form logic
    (Phase 3's job), no new review/trust logic (Phase 4's job) -- this
    phase integrates, renders, and rehearses what already exists.

Exit criteria:
  - Full live run of Journey D from 07_APP_FLOW.txt succeeds end to end,
    offline, on the physical kit: bilingual capture, disambiguation,
    required-field filling with at least one "I don't know," bounded
    clarification, a REVIEW correction, SUBMIT, department queue + map
    pin appearing together, and the function-call/provenance log shown
    on request.

--------------------------------------------------------------------------------
DEPENDENCY SUMMARY
--------------------------------------------------------------------------------
  Phase 1 --> Phase 2 --> [interface frozen] --> Phase 3  --\
                                              \-> Phase 4  --+--> Phase 5

  Phases 1-2 are strictly sequential and both need the kit -- get through
  them as fast as possible since nothing else can start for real until
  Phase 2's interface is frozen.
  Phases 3 and 4 start together, run independently, need no kit, and can
  genuinely happen in two different locations with two different people/
  sub-teams.
  Phase 5 cannot start until Phase 2 (real interface), Phase 3 (routing/
  form engine), and Phase 4 (review/trust layer) are all done, and it is
  the only phase besides 1-2 that needs the kit.
